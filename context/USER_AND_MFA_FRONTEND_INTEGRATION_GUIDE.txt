1. EXECUTIVE SUMMARY & DETAILED DESCRIPTION OF BACKEND CHANGES
================================================================================
The GreenLedger ESG platform has undergone major user domain upgrades to support
rich user profiles, facility-level tenancy assignment, and an enterprise-grade
Multi-Factor Authentication (MFA) system.

--------------------------------------------------------------------------------
1.1. User Model Schema Enhancements
--------------------------------------------------------------------------------
Four new columns have been added to the `users` table:
1. `background` (Text, Nullable):
   - Stores the URL or asset path for the user's custom header/banner image.
   - Ideal for profile page customization and tenant dashboard cards.
2. `logo` (Text, Nullable):
   - Stores the URL or asset path for the user's profile avatar / picture.
   - If null, the frontend should fall back to user initials or a default avatar.
3. `bio` (Text, Nullable):
   - Stores a personal or professional description / biography of the user.
4. `assigned_facility_id` (UUID, Nullable, Foreign Key -> `facilities.id`):
   - Associates a user directly with a specific facility within their tenant.
   - Configured with `ON DELETE SET NULL` so deleting a facility does not delete
     assigned users.
   - In Python/SQLAlchemy, `assigned_facility` is mapped as an alias/synonym to
     `assigned_facility_id`. Both keys are accepted and returned by the APIs.
   - Relationship `facility` is loaded to allow access to facility metadata.

In the `user_auth_sessions` table:
1. `mfa_attempts` (Integer, Default 0):
   - Tracks failed OTP verification attempts to prevent brute-force attacks.

--------------------------------------------------------------------------------
1.2. Multi-Factor Authentication (MFA) Production-Grade Architecture
--------------------------------------------------------------------------------
MFA is now fully functional, secure, and production-ready:
1. Two-Stage Login Handshake:
   - When a user logs in via `POST /api/v1/user/auth/login`:
     * If `user.mfa_enabled == False`: Normal tokens (`access_token`,
       `refresh_token`) are returned immediately.
     * If `user.mfa_enabled == True`: Tokens are NOT returned. The backend creates
       a pending MFA challenge, generates a cryptographically random 6-digit OTP,
       hashes the OTP using SHA-256 in the database, sets an expiration timestamp
       (10 minutes), and sends an email to the user.
     * The response returns `{ "mfa_required": true, "session_identifier": "..." }`.
2. Professional HTML Email Template:
   - Dispatches a modern, mobile-responsive HTML email matching GreenLedger's
     design system (emerald `#10B981` accents, high-contrast monospace 6-digit
     code card, 10-minute expiration badge, and security advisories).
3. Brute-Force Rate Limiting (5 Attempts):
   - In `POST /api/v1/user/auth/mfa/verify`, each invalid code increments
     `mfa_attempts`.
   - If failed attempts reach 5, the session is revoked immediately, forcing the
     user to restart login.
4. Resend Endpoint:
   - `POST /api/v1/user/auth/mfa/resend` generates a new 6-digit code, resets
     attempts to 0, extends validity by 10 minutes, and emails the user.
5. Self-Service MFA Toggle:
   - Authenticated users can enable or disable MFA on their own account at
     `POST /api/v1/user/auth/mfa/toggle`, requiring confirmation of their current
     account password.
6. Audit Trail Logging:
   - Every MFA event (`USER_MFA_ENABLED`, `USER_MFA_DISABLED`,
     `USER_MFA_VERIFICATION_SUCCESS`, `USER_MFA_VERIFICATION_FAILED`) is logged
     to the tenant audit trail.

--------------------------------------------------------------------------------
1.3. Facility Assignment & Tenant Isolation Validation
--------------------------------------------------------------------------------
When an admin creates (`POST /api/v1/user`) or updates (`PATCH /api/v1/user/{id}`)
a user with an `assigned_facility_id`:
- The backend verifies that the specified facility exists and belongs to the
  caller's tenant.
- If the facility does not exist or belongs to another tenant, the backend halts
  with `HTTP 404 Not Found` (`FACILITY_NOT_FOUND`).
- The user listing endpoint (`GET /api/v1/user`) supports filtering users by
  `assigned_facility_id`.

2. API RESPONSE ENVELOPE & GLOBAL ERROR SPECIFICATION
================================================================================

--------------------------------------------------------------------------------
2.1. Standard Success Envelope: APIResponse[T]
--------------------------------------------------------------------------------
Every single API endpoint returns data wrapped in the standard `APIResponse[T]`
envelope. The frontend client should unwrap `.data` from this structure:

```json
{
  "success": true,
  "status_code": 200,
  "message": "Success",
  "data": { ... },
  "error": null,
  "method": "POST",
  "path": "/api/v1/user/auth/login",
  "timestamp": "2026-11-26T07:20:27.123456Z"
}
```

Envelope Fields:
- `success` (boolean): `true` when status_code is in the 2xx range (200-299).
- `status_code` (integer): HTTP status code (200, 201, etc.).
- `message` (string): Human-readable confirmation message.
- `data` (object | array | null): Payload payload containing the requested resource.
- `error` (null): Null on successful responses.
- `method` (string): HTTP method of the request ("GET", "POST", "PATCH", etc.).
- `path` (string): Request URL path.
- `timestamp` (string ISO-8601): UTC timestamp of response generation.

--------------------------------------------------------------------------------
2.2. Standard Error Envelope: APIError
--------------------------------------------------------------------------------
When an error occurs, the backend returns `success: false` with the `error` object:

```json
{
  "success": false,
  "status_code": 401,
  "message": "Invalid verification code",
  "data": null,
  "error": {
    "error_code": "AUTH_INVALID_CREDENTIALS",
    "detail": "Invalid verification code",
    "validation": null
  },
  "method": "POST",
  "path": "/api/v1/user/auth/mfa/verify",
  "timestamp": "2026-11-26T07:21:00.000000Z"
}
```

For Pydantic validation errors (HTTP 422):
```json
{
  "success": false,
  "status_code": 422,
  "message": "Request validation failed",
  "data": null,
  "error": {
    "error_code": "VALIDATION_ERROR",
    "detail": "Invalid fields in request payload",
    "validation": [
      {
        "field": "password",
        "message": "String should have at least 8 characters",
        "type": "string_too_short"
      }
    ]
  },
  "method": "POST",
  "path": "/api/v1/user/auth/login",
  "timestamp": "2026-11-26T07:21:00.000000Z"
}
```

--------------------------------------------------------------------------------
2.3. Exhaustive Error Codes Reference Table
--------------------------------------------------------------------------------
| HTTP Status | Error Code (`error_code`) | Trigger Reason & Recommended Frontend Action |
|-------------|---------------------------|-----------------------------------------------|
| 400 | `USER_INVALID_ROLE` | The provided role string is not in `UserRole`. |
| 400 | `USER_LAST_ACTIVE_ADMIN` | Cannot deactivate or demote the last active admin. |
| 400 | `USER_CANNOT_DELETE_OWNER` | Cannot delete the tenant owner account. |
| 401 | `AUTH_REQUIRED` | Missing or malformed `Authorization: Bearer <token>` header. |
| 401 | `AUTH_INVALID_CREDENTIALS` | Invalid email/password, or incorrect MFA OTP code entered. |
| 401 | `AUTH_TOKEN_EXPIRED` | JWT token expired, MFA code expired, or max OTP attempts (5) reached. |
| 401 | `AUTH_INVALID_REFRESH_TOKEN` | Invalid refresh token or invalid MFA session identifier. |
| 401 | `AUTH_SESSION_REVOKED` | User logged out or session was revoked. Redirect to login. |
| 403 | `AUTH_PERMISSION_DENIED` | User lacks required RBAC permission or is inactive. |
| 403 | `USER_INACTIVE` | Account has been deactivated. Inform user to contact admin. |
| 404 | `USER_NOT_FOUND` | User ID was not found in the current tenant. |
| 404 | `FACILITY_NOT_FOUND` | The provided `assigned_facility_id` does not exist in tenant. |
| 409 | `USER_ALREADY_EXISTS` | Email address is already registered in the system. |
| 422 | `VALIDATION_ERROR` | Schema validation error (e.g. empty names, invalid email). |

3.1. POST /api/v1/user/auth/login (MODIFIED - MFA Handshake)
--------------------------------------------------------------------------------
Authenticates user credentials. If MFA is enabled, triggers an OTP email and
returns a challenge token instead of JWT tokens.

- Method: POST
- URL: `/api/v1/user/auth/login` (trailing slash `/api/v1/user/auth/login/` also supported)
- Auth: Public (No token required)
- Headers: `Content-Type: application/json`

Request Body:
```json
{
  "email": "jane.doe@greenledgeresg.com",
  "password": "SecurePassword123!"
}
```
Field Specifications:
- `email` (string, required): Valid email address.
- `password` (string, min_length=8, required): Account password.

Response (Case A: User has MFA DISABLED):
```json
{
  "success": true,
  "status_code": 200,
  "message": "Success",
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiIs...",
    "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
    "expires_in": 86400,
    "refresh_expires_in": 604800,
    "mfa_required": false,
    "session_identifier": null
  },
  "error": null,
  "method": "POST",
  "path": "/api/v1/user/auth/login",
  "timestamp": "2026-11-26T07:25:00.000000Z"
}
```

Response (Case B: User has MFA ENABLED):
```json
{
  "success": true,
  "status_code": 200,
  "message": "Success",
  "data": {
    "access_token": null,
    "refresh_token": null,
    "expires_in": null,
    "refresh_expires_in": null,
    "mfa_required": true,
    "session_identifier": "aB3_9zQk1mPxRt..."
  },
  "error": null,
  "method": "POST",
  "path": "/api/v1/user/auth/login",
  "timestamp": "2026-11-26T07:25:00.000000Z"
}
```

Frontend Handling Logic:
- If `data.mfa_required === true`:
  * Store `data.session_identifier` in component state (or temporary session store).
  * Do NOT route to Dashboard. Transition the UI to the "Enter 6-Digit Code" modal.
- If `data.mfa_required === false`:
  * Store `access_token` and `refresh_token` in auth storage. Route to Dashboard.

3.2. POST /api/v1/user/auth/mfa/verify (MODIFIED - Rate-Limited OTP Check)
--------------------------------------------------------------------------------
Verifies the 6-digit OTP code received by the user via email.

- Method: POST
- URL: `/api/v1/user/auth/mfa/verify`
- Auth: Public (No token required)
- Headers: `Content-Type: application/json`

Request Body:
```json
{
  "session_identifier": "aB3_9zQk1mPxRt...",
  "code": "729401"
}
```
Field Specifications:
- `session_identifier` (string, required): The session identifier received from login.
- `code` (string, min_length=4, max_length=10, required): The 6-digit OTP code.

Response (Success):
```json
{
  "success": true,
  "status_code": 200,
  "message": "Success",
  "data": {
    "access_token": "eyJhbGciOiJIUzI1NiIs...",
    "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
    "expires_in": 86400,
    "refresh_expires_in": 604800,
    "mfa_required": false,
    "session_identifier": null
  },
  "error": null,
  "method": "POST",
  "path": "/api/v1/user/auth/mfa/verify",
  "timestamp": "2026-11-26T07:25:30.000000Z"
}
```

Potential Errors:
- `401 AUTH_INVALID_CREDENTIALS`: Incorrect code entered. (Inform user; show attempts left).
- `401 AUTH_TOKEN_EXPIRED`: Code has expired (>10 min) OR 5 failed attempts reached.
  (Direct user to click "Resend Code" or re-login).
- `401 AUTH_INVALID_REFRESH_TOKEN`: Session identifier is invalid or already completed.

--------------------------------------------------------------------------------
3.3. POST /api/v1/user/auth/mfa/resend (NEW - Resend 6-Digit OTP)
--------------------------------------------------------------------------------
Generates and sends a new 6-digit verification code to the user's email, resets
the attempt counter, and extends code validity by 10 minutes.

- Method: POST
- URL: `/api/v1/user/auth/mfa/resend`
- Auth: Public (No token required)
- Headers: `Content-Type: application/json`

Request Body:
```json
{
  "session_identifier": "aB3_9zQk1mPxRt..."
}
```

Response (Success):
```json
{
  "success": true,
  "status_code": 200,
  "message": "Verification code resent successfully",
  "data": {
    "session_identifier": "aB3_9zQk1mPxRt...",
    "message": "Verification code has been resent to your registered email address."
  },
  "error": null,
  "method": "POST",
  "path": "/api/v1/user/auth/mfa/resend",
  "timestamp": "2026-11-26T07:26:00.000000Z"
}
```

Frontend Handling Logic:
- Disable the "Resend Code" button for 30 or 60 seconds after clicking to prevent
  accidental spamming, showing a countdown timer.

--------------------------------------------------------------------------------
3.4. POST /api/v1/user/auth/mfa/toggle (NEW - Self-Service MFA Toggle)
--------------------------------------------------------------------------------
Enables or disables MFA on the authenticated user's account. Requires password
verification for security.

- Method: POST
- URL: `/api/v1/user/auth/mfa/toggle`
- Auth: Protected (`Authorization: Bearer <access_token>`)
- Headers: `Content-Type: application/json`

Request Body:
```json
{
  "password": "CurrentPassword123!",
  "mfa_enabled": true
}
```
Field Specifications:
- `password` (string, required): Current account password.
- `mfa_enabled` (boolean, required): `true` to enable MFA, `false` to disable MFA.

Response (Success):
```json
{
  "success": true,
  "status_code": 200,
  "message": "Success",
  "data": {
    "mfa_enabled": true,
    "message": "MFA has been successfully enabled."
  },
  "error": null,
  "method": "POST",
  "path": "/api/v1/user/auth/mfa/toggle",
  "timestamp": "2026-11-26T07:27:00.000000Z"
}
```

Potential Errors:
- `401 AUTH_INVALID_CREDENTIALS`: Incorrect password supplied.
- `401 AUTH_REQUIRED`: Missing or expired access token.

5. FRONTEND UX WORKFLOWS & STATE MACHINES
================================================================================

--------------------------------------------------------------------------------
5.1. Authentication Flow (Dual-Stage Login with MFA Challenge)
--------------------------------------------------------------------------------
State Machine Flow Diagram:

   [User Enters Email & Password]
                 │
                 ▼
     POST /api/v1/user/auth/login
                 │
      ┌──────────┴──────────┐
      ▼                     ▼
[mfa_required == false]   [mfa_required == true]
      │                     │
      │                     ├── Store session_identifier in state
      │                     ├── Switch UI: "Enter 6-Digit Code"
      │                     └── Start 60s countdown for "Resend Code" button
      │                                    │
      │                                    ▼
      │                      [User Submits Code / Resends]
      │                        ┌───────────┴───────────┐
      │                        ▼                       ▼
      │              (User clicks Resend)      (User submits Code)
      │                        │                       │
      │             POST .../mfa/resend      POST .../mfa/verify
      │             (Resets 60s timer)                 │
      │                                                ▼
      │                                     [Code Valid? (max 5 tries)]
      │                                        ┌───────┴───────┐
      │                                        ▼               ▼
      │                                     (Valid)       (Invalid/Expired)
      │                                        │               │
      │                                        │          Show error banner
      │                                        │          (If 5 fails -> re-login)
      ▼                                        ▼
[Store access_token & refresh_token -> Navigate to Dashboard /me]

Recommended UI Guidelines:
1. Monospace 6-Digit Input: Use 6 individual input boxes or a single formatted
   input with `font-family: monospace; letter-spacing: 0.5em; font-size: 24px;`.
2. Auto-Focus & Auto-Submit: Auto-advance cursor as each digit is typed; auto-submit
   when the 6th digit is entered.
3. Resend OTP Button: Disable for 60 seconds with live countdown
   (`Resend Code in 45s`).
4. Attempt Feedback: If `401 AUTH_INVALID_CREDENTIALS` is received, alert the user
   ("Invalid verification code. Please check your email and try again.").

--------------------------------------------------------------------------------
5.2. Profile Settings View (Avatar, Banner, Bio, MFA Toggle)
--------------------------------------------------------------------------------
UI Layout:
1. Cover Photo / Banner:
   - Displays `background` URL. A button overlay allows users to paste an image URL
     or upload via the tenant uploads endpoint.
2. Avatar / Logo:
   - Displays `logo` URL in a circular badge. Falls back to user initials if null.
3. Bio Field:
   - Multi-line textarea for `bio` with a 500-character counter.
4. Basic Information:
   - Inputs for `first_name`, `last_name`, `phone_number`, `job_title`.
   - Action: "Save Profile Changes" dispatches `PATCH /api/v1/user/auth/me`.
5. Security & MFA Card:
   - Displays a badge indicating MFA Status (`Enabled` in green or `Disabled` in gray).
   - Toggle switch for MFA.
   - When clicked, opens a Confirmation Modal:
     * "Enter your current password to enable/disable Multi-Factor Authentication".
     * Password input.
     * Submits to `POST /api/v1/user/auth/mfa/toggle`.
     * On success, updates the toggle and displays a toast notification.

--------------------------------------------------------------------------------
5.3. Tenant User Management View (Facility Assignment, MFA Administration)
--------------------------------------------------------------------------------
1. User Table:
   - Columns: Avatar (`logo`), Full Name, Email, Role badge, Assigned Facility,
     MFA status badge, Active status, Actions.
   - Facility Column: Displays facility name. If `assigned_facility_id` is null,
     displays `All Facilities` or `Unassigned`.
   - Filter Bar: Allows filtering the table by facility using a dropdown populated
     from `GET /api/v1/facility`, which passes `?assigned_facility_id=<id>`.
2. Add / Edit User Drawer:
   - Includes dropdown: `Assign Facility` (populated with active tenant facilities).
   - Includes checkbox/switch: `Enable MFA for this user` (sets `mfa_enabled`).
   - Includes text fields for `bio`, `logo` URL, and `background` URL.
