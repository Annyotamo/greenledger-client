1. EXECUTIVE SUMMARY & ARCHITECTURAL PHILOSOPHY
================================================================================
GreenLedger ESG Server uses a production-grade dual-tier authorization model:
  Tier 1: High-level User Roles (TENANT_OWNER, TENANT_ADMIN, ESG_TEAM,
          FACILITY_HEAD, AUDITOR).
  Tier 2: Fine-grained Component Permissions across 19 individual features
          with 4 hierarchical access levels (NONE < READ < WRITE < ADMIN).

Backend Security Rule:
  The backend is the ultimate gatekeeper. Every single API route is protected by
  FastAPI dependency injection (`require_read`, `require_write`, `require_admin`).
  If a user lacks permission, the backend immediately halts execution and returns:
    HTTP 403 Forbidden -> error_code: "AUTH_PERMISSION_DENIED"

Frontend UX Rule:
  The frontend must NEVER let a user stumble upon a broken page or raw 403 error.
  Instead, the frontend provides a seamless 3-layer defense:
    1. Do not show restricted navigation links in the sidebar or navbar.
    2. If the user manually types a restricted URL in the browser address bar,
       intercept it BEFORE the page content mounts.
    3. Show a polished "Access Restricted" dialog explaining why they cannot enter,
       and automatically redirect them after a short countdown (e.g., 5 seconds)
       back to their previous page or to the main Dashboard.

2. CORE CONCEPTS: ROLES, FEATURE KEYS (19 COMPONENTS), ACCESS LEVELS (4 POWERS)
================================================================================

--------------------------------------------------------------------------------
A. ROLES (User's Primary Persona)
--------------------------------------------------------------------------------
Every user in the tenant has one primary role:
  - TENANT_OWNER:  Organization account creator. Permanent full superuser.
  - TENANT_ADMIN:  Organization administrator. Full superuser.
  - ESG_TEAM:      Sustainability officer entering emissions data across modules.
  - FACILITY_HEAD: Site/plant manager reporting on-site electricity and fuel.
  - AUDITOR:       Internal/external compliance auditor reviewing reports.

--------------------------------------------------------------------------------
B. THE 19 FEATURE KEYS (Components)
--------------------------------------------------------------------------------
All application modules are mapped to 19 standard string keys:
  GHG PROTOCOL MODULES:
    1.  "scope_1"            -> Scope 1 Direct Combustion (Fuel, Boilers, Fleet)
    2.  "scope_2"            -> Scope 2 Indirect Electricity & Renewable Power
    3.  "scope_3_cat1"       -> Scope 3 Cat 1: Purchased Goods and Services
    4.  "scope_3_cat2"       -> Scope 3 Cat 2: Capital Goods
    5.  "scope_3_cat3"       -> Scope 3 Cat 3: Fuel & Energy Related (WTT)
    6.  "scope_3_cat4"       -> Scope 3 Cat 4: Upstream Transportation & Freighting
    7.  "scope_3_cat5"       -> Scope 3 Cat 5: Waste Generated in Operations
    8.  "scope_3_cat6"       -> Scope 3 Cat 6: Business Travel (Air, Rail, Hotel)
    9.  "scope_3_cat7"       -> Scope 3 Cat 7: Employee Commuting
    10. "scope_3_cat9"       -> Scope 3 Cat 9: Downstream Transportation
    11. "scope_3_cat15"      -> Scope 3 Cat 15: Investments & Financed Emissions

  STANDARDS & DISCLOSURES:
    12. "brsr"               -> India BRSR Sustainability Reports (Principles 1-9)
    13. "cbam"               -> European Union CBAM Setup & Communication Reports
    14. "eia"                -> Industrial Chimney Stack Air Emissions Monitoring

  ORGANIZATION INFRASTRUCTURE:
    15. "facilities"         -> Plants, Offices, Sub-Units, and Meters
    16. "reporting_periods"  -> Accounting Periods & Period Locking

  PERFORMANCE & GOVERNANCE:
    17. "analytics"          -> GHG Protocol Dashboards & Energy Consumption Analytics
    18. "team_members"       -> User & Team Member Management (Invites, Roles, Permissions)
    19. "audit_trails"       -> Immutable Regulatory Audit Logs

--------------------------------------------------------------------------------
C. THE 4 ACCESS LEVELS (Power Hierarchy)
--------------------------------------------------------------------------------
Each of the 19 features has one assigned level for the user:
  LEVEL 0: "none"   (Rank 0)  -> No access. Module hidden. Route blocked.
  LEVEL 1: "read"   (Rank 10) -> Can view tables, search, filter, export Excel/PDF.
                                 Cannot add, edit, or delete anything.
  LEVEL 2: "write"  (Rank 20) -> Can view + create activities, edit drafts,
                                 delete drafts, submit for approval.
                                 Cannot formally verify/approve or lock periods.
  LEVEL 3: "admin"  (Rank 30) -> Can view + write + approve/verify/reject activities,
                                 lock/archive periods, and edit team permissions.

Hierarchy Formula:
  ADMIN (30) >= WRITE (20) >= READ (10) >= NONE (0)
  If a page or button requires "write", a user with "write" or "admin" has access.
  A user with "read" or "none" does NOT have access.

3.3. HOW FRONTEND CONSUMES THIS DATA
--------------------------------------------------------------------------------
Store both in your global auth store (Zustand, Pinia, Redux, or React Context):
1. `ui_navigation`: Directly controls sidebar / navbar rendering.
   - Example: `if (ui_navigation.team_members) renderMenuItem("/team-members")`
   - Example: `if (ui_navigation.scope_3_categories.cat1_spend) renderSubMenu(...)`
2. `permissions` (or `effective_permissions`): Controls route guards and button states.
   - Example: `canWrite("scope_1")` -> checks `permissions["scope_1"] >= "write"`
   - Example: `canAdmin("team_members")` -> checks `permissions["team_members"] >= "admin"`

4. HOW TO HANDLE ROLE-BASED & PERMISSION-BASED BLOCKING
================================================================================
When a user does not have permission for a module (e.g. `team_members` is "none"),
here is the complete production workflow for the frontend:

--------------------------------------------------------------------------------
4.1. NAVIGATION MENU RENDERING (PREVENTIVE LAYER)
--------------------------------------------------------------------------------
- Never show a link to a page the user cannot access.
- In your Sidebar/Navbar component, filter navigation items using `ui_navigation`:
  const navItems = [
    { title: "Dashboard", path: "/dashboard", visible: true },
    { title: "Scope 1 - Fuel", path: "/activities/fuel", visible: uiNav.scope_1 },
    { title: "Scope 2 - Electricity", path: "/activities/electricity", visible: uiNav.scope_2 },
    { title: "BRSR Reports", path: "/reports/brsr", visible: uiNav.brsr },
    { title: "EU CBAM", path: "/reports/cbam", visible: uiNav.cbam },
    { title: "Team Members", path: "/team-members", visible: uiNav.team_members },
    { title: "Audit Trail", path: "/audit-logs", visible: uiNav.audit_trails },
  ];
- If `visible === false`, the link is NOT rendered in the DOM.

--------------------------------------------------------------------------------
4.2. ROUTE GUARDS & URL FORCING (PROACTIVE LAYER)
--------------------------------------------------------------------------------
What if user Bob (who has "none" on `team_members`) types:
  `https://app.greenledger.com/team-members` directly in the address bar?

OR clicks an old bookmark / copy-pasted link?

DO NOT:
  - Do NOT render the Team Members page.
  - Do NOT let the page fire API requests (which will fail with 403 anyway).
  - Do NOT show a flash of content before redirecting.

DO:
  - The Frontend Route Guard (e.g. `<ProtectedRoute feature="team_members" minLevel="read">`)
    inspects the user's `permissions["team_members"]`.
  - It detects `permissions["team_members"] === "none"`.
  - It IMMEDIATELY blocks the route component from mounting.
  - It renders the Access Denied Dialog with an auto-redirect timer.

--------------------------------------------------------------------------------
4.3. THE ACCESS DENIED DIALOG & AUTO-REDIRECT (REACTIVE LAYER - RECOMMENDED)
--------------------------------------------------------------------------------
The user's suggestion of showing a dialog message and auto-redirecting is an
exceptional UX pattern because:
  1. It avoids confusing the user (an instant silent redirect makes users think
     the app is broken or lagging).
  2. It explicitly informs the user that their role/permissions do not grant
     access to this section.
  3. It gives them immediate action choices ("Go Back", "Go to Dashboard")
     while also auto-redirecting after 5 seconds if they do nothing.

Specification for the Access Denied Dialog:
  +-------------------------------------------------------------------------+
  |  [ ! ] Access Restricted                                                |
  +-------------------------------------------------------------------------+
  |  You do not have permission to view the Team Members management module. |
  |                                                                         |
  |  Your role (ESG_TEAM) does not have access granted for this component.  |
  |  If you need access, please contact your organization administrator.    |
  |                                                                         |
  |  Redirecting to Dashboard in 5 seconds... [||||||||||||||||----]        |
  +-------------------------------------------------------------------------+
  |           [ Go Back to Previous Page ]     [ Go to Dashboard Now ]      |
  +-------------------------------------------------------------------------+

Key Engineering Details for this Dialog:
  1. Countdown Timer: Start a 5-second interval timer (`setInterval`).
  2. Progress Bar: Animate a progress bar or show `(Redirecting in X seconds...)`.
  3. Safe Navigation:
     - If the user has a valid previous page in browser history (e.g. was on `/dashboard`
       or `/activities/fuel`), clicking "Go Back" calls `router.back()`.
     - When the 5-second timer runs out, navigate to `/dashboard`.
  4. Cleanup: ALWAYS clear the timer (`clearInterval`) in the component unmount
     lifecycle to prevent memory leaks and zombie redirects!

--------------------------------------------------------------------------------
4.4. COMPARISON: DIALOG WITH TIMER VS. INSTANT TOAST REDIRECT
--------------------------------------------------------------------------------
Approach A: Access Denied Dialog with Countdown (User's Suggestion)
  - Pros: Cleanest enterprise UX. Clear, educational, allows the user to read why
    they were blocked, offers explicit buttons.
  - Recommended for: Main modules and sensitive settings pages (Team Members,
    Audit Logs, CBAM, BRSR).

Approach B: Instant Silent Redirect + Notification Toast
  - Pros: Very fast, fewer clicks.
  - Cons: Can feel jarring or disorienting if the user intentionally typed the URL.
  - Recommended for: Minor deep-link tabs or child sub-routes.

Verdict: Implement Approach A (Access Denied Dialog with countdown) for all top-level
page routes. It provides the highest quality enterprise grade experience.

5. BUTTON & ACTION-LEVEL PERMISSIONS (SHOW / HIDE VS. DISABLE)
================================================================================
Within pages that the user CAN see (e.g., user has "read" on Scope 1), their
experience on individual buttons must match their AccessLevel.

--------------------------------------------------------------------------------
5.1. BEHAVIOR MATRIX BY ACCESS LEVEL
--------------------------------------------------------------------------------
Component Feature: "scope_1" (Fuel Activities)

| Action / Button            | Level: NONE  | Level: READ   | Level: WRITE  | Level: ADMIN  |
|----------------------------|--------------|---------------|---------------|---------------|
| View Table / Search / Filter| BLOCKED (403)| ENABLED       | ENABLED       | ENABLED       |
| Export to Excel / PDF       | BLOCKED (403)| ENABLED       | ENABLED       | ENABLED       |
| "Add Activity" Button      | BLOCKED (403)| DISABLED/HIDE | ENABLED       | ENABLED       |
| "Edit Activity" (Draft)    | BLOCKED (403)| DISABLED/HIDE | ENABLED       | ENABLED       |
| "Delete Activity" (Draft)  | BLOCKED (403)| DISABLED/HIDE | ENABLED       | ENABLED       |
| "Submit for Verification"  | BLOCKED (403)| DISABLED/HIDE | ENABLED       | ENABLED       |
| "Verify / Approve" Button  | BLOCKED (403)| DISABLED/HIDE | DISABLED/HIDE | ENABLED       |
| "Reject" Button            | BLOCKED (403)| DISABLED/HIDE | DISABLED/HIDE | ENABLED       |

--------------------------------------------------------------------------------
5.2. HIDE VS. DISABLE GUIDELINES
--------------------------------------------------------------------------------
- Recommendation:
  * For PRIMARY actions (e.g. "+ Add Activity", "Export Excel"): Keep the button
    VISIBLE but DISABLED with a Tooltip:
      Tooltip: "Your access level (read-only) does not allow creating activities."
    Why? It prevents users from wondering "Where did the Add button go? Is this a bug?".
  * For ADMINISTRATIVE actions (e.g. "Verify", "Reject", "Lock Period"): HIDE the
    button completely for non-admin users to keep the interface clutter-free.

6. GLOBAL API CLIENT & 403 ERROR INTERCEPTOR
================================================================================
Even with frontend guards, network latency or stale tabs could cause an API request
to fail with 403. The frontend HTTP client (Axios or Fetch wrapper) must handle
this globally.

--------------------------------------------------------------------------------
6.1. BACKEND 403 RESPONSE PAYLOAD
--------------------------------------------------------------------------------
When any API call is blocked by RBAC, the backend returns:
{
  "success": false,
  "status_code": 403,
  "message": "You do not have 'write' permission for component 'scope_1'",
  "data": null,
  "error": {
    "error_code": "AUTH_PERMISSION_DENIED",
    "detail": "Action prohibited by access control policy.",
    "validation": null
  },
  "method": "POST",
  "path": "/api/v1/tenant/activity/fuel",
  "timestamp": "2026-11-23T04:00:00Z"
}

--------------------------------------------------------------------------------
6.2. AXIOS INTERCEPTOR LOGIC
--------------------------------------------------------------------------------
In your global Axios instance:
  api.interceptors.response.use(
    (response) => response,
    (error) => {
      if (error.response?.status === 403) {
        const errorCode = error.response.data?.error?.error_code;
        const message = error.response.data?.message || "Permission Denied";

        if (errorCode === "AUTH_PERMISSION_DENIED") {
          // Trigger global notification or modal dialog
          NotificationService.error({
            title: "Access Restricted",
            description: message,
            duration: 6000,
          });
        }
      }
      return Promise.reject(error);
    }
  );

--------------------------------------------------------------------------------
Saving:
  Call: `PATCH /api/v1/tenant/user/{user_id}/permissions`

      "scope_1": "none",
      "cbam": "write",
      "team_members": "read"

  Clicking "Reset All to Defaults" sends:
  {
    "custom_permissions": {}
  }
  Instantly clears all overrides and resets user back to their clean role defaults.

--------------------------------------------------------------------------------
8.2. PERMISSION CHECKING UTILITIES (src/utils/rbac.utils.ts)
--------------------------------------------------------------------------------
```typescript
import { AccessLevel, FeatureKey, UserProfile } from "../types/rbac.types";

const ACCESS_RANK: Record<AccessLevel, number> = {
  none: 0,
  read: 10,
  write: 20,
  admin: 30,
};

/**
 * Compare two access levels.
 * Returns true if userLevel meets or exceeds requiredLevel.
 */
export function hasAccess(userLevel: AccessLevel | undefined, requiredLevel: AccessLevel): boolean {
  const current = ACCESS_RANK[userLevel || "none"] ?? 0;
  const target = ACCESS_RANK[requiredLevel] ?? 0;
  return current >= target;
}

/**
 * Check if the current user has permission for a specific feature.
 * Automatically grants access if the user is TENANT_OWNER or TENANT_ADMIN.
 */
export function checkPermission(
  user: UserProfile | null,
  feature: FeatureKey,
  requiredLevel: AccessLevel = "read"
): boolean {
  if (!user) return false;
  if (user.role === "TENANT_OWNER" || user.role === "TENANT_ADMIN") return true;

  const currentLevel = user.permissions?.[feature] ?? "none";
  return hasAccess(currentLevel, requiredLevel);
}
```

```typescript
// src/hooks/usePermission.ts
import { useAuth } from "../context/AuthContext";
import { FeatureKey, AccessLevel } from "../types/rbac.types";
import { checkPermission } from "../utils/rbac.utils";

export function usePermission(feature: FeatureKey, requiredLevel: AccessLevel = "read") {
  const { user } = useAuth();
  const allowed = checkPermission(user, feature, requiredLevel);
  const currentLevel = user?.permissions?.[feature] ?? "none";

  return {
    allowed,
    currentLevel,
    canRead: checkPermission(user, feature, "read"),
    canWrite: checkPermission(user, feature, "write"),
    canAdmin: checkPermission(user, feature, "admin"),
  };
}
```

```tsx
interface ProtectedRouteProps {

}

export const ProtectedRoute: React.FC<ProtectedRouteProps> = ({
  feature,
  requiredLevel = "read",
  featureTitle,
  children,
}) => {
  const { allowed } = usePermission(feature, requiredLevel);
  const navigate = useNavigate();
  const location = useLocation();

  const [secondsLeft, setSecondsLeft] = useState(5);

  useEffect(() => {
    if (allowed) return;

    // Countdown interval

      setSecondsLeft((prev) => {
        if (prev <= 1) {
          clearInterval(interval);
          navigate("/dashboard", { replace: true });
          return 0;
        }
        return prev - 1;
      });

    return () => clearInterval(interval);

  if (allowed) {
    return <>{children}</>;
  }

  // If user does not have permission, show the Access Denied Dialog
```

```typescript
// src/api/apiClient.ts
import axios from "axios";

export const apiClient = axios.create({
  baseURL: "/api/v1",
  timeout: 15000,
  headers: {
    "Content-Type": "application/json",
  },
});

apiClient.interceptors.request.use((config) => {
  const token = localStorage.getItem("access_token");
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

apiClient.interceptors.response.use(
  (response) => response,
  (error) => {
    if (error.response?.status === 403) {
      const errorData = error.response.data;
      const errorCode = errorData?.error?.error_code;
      const message = errorData?.message || "You do not have permission to perform this action.";

      if (errorCode === "AUTH_PERMISSION_DENIED") {
        console.warn(`[RBAC] Access denied: ${message}`);
        // Dispatch custom global event or trigger your UI Toast notification
        window.dispatchEvent(
          new CustomEvent("app:access-denied", {
            detail: { message },
          })
        );
      }
    }
    return Promise.reject(error);
  }
);
```
